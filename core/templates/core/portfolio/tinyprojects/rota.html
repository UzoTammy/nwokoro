    How I solved it, step by step.

    Designed for CP Devotional's publishing team, then built and proven here first. Each step shows the question, the decision and the code.

    1. 01

      Turn the calendar into slots

      Question: what exactly needs an owner?

      Not "days" but slots: one piece of content due on one date. A daily devotion makes 28 slots in four weeks; music and stories add one a week each.

      Decision: describe each content type by the weekday it runs on, and generate slots oldest first, so earlier days are filled before later ones.

    2. 02

      Rule people out before ranking them

      Question: who can take this slot at all?

      Fairness only matters among people who are actually free. Five hard rules come first: not away, not already writing that day, not over three slots that week, not back-to-back, and not someone who already missed this slot.

      Decision: every rule returns a reason, so the page can say exactly why someone was skipped.

        return False, 'already missed this slot'

    3. 03

      Measure fairness relative to capacity

      Question: is giving everyone the same number of slots fair?

      No. Someone with time for ten pieces a month isn't overworked by four, but someone with time for five is nearly full at four. So load is slots held divided by capacity, plus a penalty for missed deadlines so reliability counts.

      Decision: L = A/K + 0.5 × M; the lowest wins.

      {% verbatim %}def load(self, pid):
    """L = A / K + 0.5 * M"""
    person = self.writers[pid]
    return self.held(pid) / person.capacity + 0.5 * person.missed

# Ada: 4 slots of 8  -> 0.50
# Ben: 3 slots of 4  -> 0.75   => Ada gets the slot{% endverbatim %}
    4. 04

      Make ties predictable

      Question: two people have the same load. Who goes?

      Random choice would make the rota impossible to test and hard to trust. The person who has gone longest without a slot goes first, and team order settles anything left.

      Decision: sort by (load, latest slot, team order). The same inputs always give the same rota.

      An empty publishing day is worse than one person writing two days in a row. So the search runs twice: strict first, then with only the back-to-back rule relaxed. The other rules never bend.

      Pick a reviewer who isn't the writer

      Question: who checks the work?

      The reviewer with the fewest unpublished reviews, and never the person who wrote it. Nobody approves their own work.

    7. 07

      Plan for missed deadlines

      Question: a writer misses the draft deadline. Now what?

      • 3 or more days left: reassign to the next fairest writer, with 24 hours to draft.
      • Less time: use a ready-made reserve piece.
      • Reserve empty: mark it missed so the reviewer steps in.

      Decision: the missed writer's M goes up, so their load rises and they're never offered that slot again.

    8. 08

      Keep the server stateless by replaying

      Question: how does "advance a day" work without storing anything?

      Because the rota is deterministic, the browser only keeps the setup and a list of actions. Each click sends them, and the server rebuilds the whole rota from scratch. Same inputs, same result, every time.

      {% verbatim %}def replay(writers, reviewers, start, actions, reserve=5):
    rota = Rota(writers, reviewers, start, reserve).generate()
    for action in actions:
        if action['type'] == 'advance':
            rota.advance()
        elif action['type'] == 'miss':
            rota.mark_will_miss(action['slot'])
    return rota{% endverbatim %}
    9. 09

      Prove it with the design's own cases

      Question: how do I know it behaves as designed?

      The tests use the examples written into the design before any code existed, plus invariants checked over a whole generated month: everyone gets a writer, nobody writes twice in a day, the weekly limit holds and nobody reviews their own work.
